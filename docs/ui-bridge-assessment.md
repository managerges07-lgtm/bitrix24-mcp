# Локальный UI-мост для шаблонов задач — оценка

**Вывод: мост не нужен и не будет реализован.** Исходная предпосылка задачи («облачный
вебхук Bitrix24 не предоставляет REST-методы для нативных шаблонов») не подтвердилась.
Проверено на портале `ges-group.bitrix24.ru` 30.08.2026.

## Что показала проверка

Семейство `tasks.template.*` доступно обычному входящему вебхуку со scope `task`:

| Метод | Статус | Параметры |
|---|---|---|
| `tasks.template.add` | работает | `fields` |
| `tasks.template.get` | работает | `templateId` |
| `tasks.template.update` | работает | `templateId`, `fields` |
| `tasks.template.delete` | работает | `templateId` |
| `tasks.template.fields` | работает | — |
| `tasks.template.list` | **сломан на портале** | любые — всегда `Unknown field definition \`filter\`` |
| `tasks.template.checklist.{add,get,list,update,delete}` | работают | `templateId`, `checkListItemId` |

Интроспекции верить нельзя: `method.get('tasks.template.add')` отвечает
`isExisting: false`, а `method.get('tasks.task.list')` — `isAvailable: false`, хотя оба
метода рабочие. Именно это и создаёт впечатление, будто шаблонов в REST нет.

Созданные так шаблоны — настоящие: видны в интерфейсе (Задачи → Шаблоны), участвуют в
автоповторе, принимают чек-лист, соисполнителей, наблюдателей и привязку к CRM.

## Почему мост не оправдан

1. **Единственный реальный пробел — сломанный `list`** — закрывается штатным `batch`:
   перебор ID по 50 за запрос, отсутствующий шаблон приходит как `false`. Это обычный
   публичный API, а не обход.
2. **Мост потребовал бы скрытых внутренних запросов.** Создание шаблона в интерфейсе идёт
   через `/bitrix/services/main/ajax.php` с `sessid`, CSRF-токеном и куками живой сессии.
   Это незадокументированный контракт: он меняется между обновлениями портала без
   предупреждения, ломается молча и требует хранить пользовательскую сессию рядом с
   MCP-сервером. Задача прямо запрещает такое без согласования — и повода нет.
3. **Стоимость эксплуатации.** Мосту нужен браузерный контекст или ретрансляция куки,
   отдельный процесс на машине пользователя и повторная авторизация при каждом
   протухании сессии — против одного HTTP-вызова через вебхук.

## Что осталось недоступным через REST (и мостом не лечится «дёшево»)

- **Пользовательские поля шаблонов.** У шаблонов своя сущность `TASKS_TASK_TEMPLATE`, и
  метода создать в ней поле нет — только интерфейс портала. Значения уже существующих
  полей шаблона через REST пишутся и читаются нормально. Поля **задач** (`TASKS_TASK`)
  создаются полностью через API — `b24_task_userfield_create`.
- **Поля `TAGS` и `XML_ID` шаблона.** REST их принимает и молча выбрасывает. Теги решены
  на стороне MCP маркером `[MCP_TAGS]: …` в описании; на задачу они переносятся уже
  настоящими тегами Битрикса.

Оба пункта — про хранение метаданных, а не про сам сценарий «создать шаблон и поставить
по нему задачу», который закрыт полностью.

## Если мост всё-таки понадобится

Осмысленный повод ровно один: массовое заведение **пользовательских полей шаблонов**,
которых в REST нет. Тогда порядок действий такой:

1. Согласовать с владельцем портала использование внутренних AJAX-эндпоинтов — письменно.
2. Не эмулировать сессию скрытно, а сделать локальное приложение Bitrix24 (placement) —
   у него есть легальный доступ к внутреннему API и понятная модель прав.
3. Держать мост отдельным процессом со своим конфигом, не смешивая с MCP-сервером: у него
   принципиально другая надёжность и другой цикл обновления.

До появления такого повода правильное решение — заводить поля шаблонов руками в
интерфейсе (это разовая операция), а всё остальное делать через REST.
